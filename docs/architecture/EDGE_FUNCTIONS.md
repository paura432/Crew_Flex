in `supabase/functions/`. Shared code in `_shared/`; business logic imported from `src/domain`
(single implementation for Next.js and Deno).

before it maps the same refusal to a plain 400 (`fromDatabaseError`), so the migration can go first. Editing the
window in progress without moving its start, `DELETE`, `PUT` and replays are unchanged.

### Requirement builder (v2 diff area 30, LOCAL `20261023600000/600100`, not deployed; BR-1.10…BR-1.15)

- **`work-requirements`** — POST and PUT take the optional terms `country` (EU-27), `timeZone` (EU IANA zones),
  `description` (≤ 4000), `shifts` (1–366, the period must be their envelope) and `conditions` (known keys only, no
  money flow), plus `intent`: `draft` saves a draft (R-D4: qualifications 0–20, no start-in-the-future rule),
  `publish` (or nothing on create) applies every rule; on PUT `publish` turns a draft into `open`. A PUT is a full
  replacement: a term not sent is cleared. They call the new RPC overloads (`create_work_requirement_idempotent` /
  `update_work_requirement` with `p_status, p_country, p_time_zone, p_description, p_shifts, p_conditions`); the old
  overloads stay for the deployed functions. Body limit **128 KB** for POST/PUT (366 shifts + a description do not fit
  in 32 KB; 413 above it). PATCH also takes `{ id, archive: true }` → `archive_work_requirement` (one way, closed or
  draft; 409 otherwise), and publishing a draft through `{ id, status: "open" }` first applies the creation rules to
  what the draft holds (400 with `issues`). GET adds `archived=include|exclude|only` (default `include`, as before) and
  every requirement carries `country`, `timeZone`, `description`, `shifts`, `conditions`, `archivedAt` (null = not
  stated). Drafts are not evaluable: `capacity-evaluate` / `matching-evaluate` answer 409 for them.
- **`matching-evaluate`** — POST `{ organizationId, startsAt, endsAt, urgency, hardQualificationTypeIds }` (strict,
  `viableCandidatesInput`, a period that has not started) → `ViableCandidatesResponse { viable }`: the live count (T-66) from RPC
  `count_viable_candidates` (DEFINER, admin/manager of that organization, a number only, never `private`
  professionals). `{ requirementId }` keeps its meaning; a body with both is 400.
- **`opportunities` / `applications`** — the requirement projection (`list_opportunities`, the card of
  `get_my_applications`) and every proposal's `terms` written since carry the same terms; older proposal versions read
  them as not stated (null). The shared schemas parse them, so an unknown key (a commission) fails loudly.

**v1.8 profile requirements (package matching-v18, LOCAL `20261023900000…200`, BR-3.7–3.13, T-80…T-87).** Every
evaluation applies them with the same engine (`evaluateMatch`):

- **`matching-evaluate` / `capacity-evaluate` / `applications` (organization side)** — `loadRequirement` reads the

  rule); candidate and applicant rows carry `candidate_declarations` (minimised, T-85), so blockers such as

- **Writes** — `apply_to_requirement` and the confirmation in `transition_application` re-check the rules in the

## Request lifecycle (`_shared/http.ts` → `createHandler`)

1. Request id: incoming `x-request-id` if it is a UUID, else a new one. Returned in body + header.
2. CORS (`_shared/cors.ts`): allowlist from `ALLOWED_ORIGINS` (comma separated; `*` ignored). Allowed
   request headers include `idempotency-key`.
   Default dev origins: `http://localhost:3000`, `http://127.0.0.1:3000`.
3. Method dispatch.
4. Handler: `requireActor` (JWT via `supabase.auth.getClaims`) → authorization from DB
   (`requireOrganizationRole`) → `parseJsonBody` / `parseQuery` (strict Zod) → domain → response.
   `parseJsonBody` refuses bodies over 32 KB (`MAX_BODY_BYTES`, 413); a route whose largest valid body is bigger
   passes its own `maxBytes` — only the `professional-profile` PATCH (128 KB, `PASSPORT_BODY_MAX_BYTES`, LOCAL,
   package passport: its largest valid body is ~80 KB, proven by a test).
5. Errors normalized (`_shared/errors.ts`); DB messages never forwarded.

## Idempotent creates (`Idempotency-Key`, remediation 2026-10-15, I-1)

The three create endpoints (`work-requirements` POST, `professional-availability` POST,
`professional-qualifications` POST) accept `Idempotency-Key: <uuid>`; `professional-logbook` POST (operation
`logbook_entry.create`, LOCAL) and `applications` POST and PATCH **require** it
(400 without it; operations `application.create` / `application.transition`; the key is claimed before the state
and version checks, so a replay returns its original result). The web app generates one key per
logical operation in the browser (`src/lib/idempotency.ts`: the same payload reuses the key until a
confirmed success; a different payload gets a new key), validates it in the server action and forwards it.
PostgreSQL enforces it (`app_private.idempotency_keys`, migration `20261015130200`): the key is scoped to
(JWT subject, operation), the request hash is computed in SQL from the canonical parameters, and the key is
claimed **in the same transaction** that creates the resource — a concurrent duplicate waits on the unique
index and then replays; a failed operation leaves no key. Responses: `201` created, `200` replay of the
original resource, `409 CONFLICT` same key with a different payload, `400` malformed key. A missing header
falls back to a fresh key (no deduplication) so older clients keep working. PATCH/DELETE are naturally
idempotent (full replacement / delete by id) and were not changed.

Never answer a `40001` from our own SQL: PostgREST retries serialization failures automatically and a
deterministic 40001 loops (observed in the local E2E run; the passport conflict uses `CF412`). 6. One structured log line: `fn, requestId, method, status, durationMs, actorId, errorCode, internal`
(error class name only). Never headers, tokens, passwords, payloads.

**Recruiter (PKG recruiter, LOCAL `20261024500100`, BR-27).** `work-requirements` `POST`/`PUT` accept
`onBehalfOfClientId` (full replacement; the 17-argument RPC overloads) and turn the database's client refusals into an
error on that field — `CFR01` → 400 `onBehalfOfClientId: v.requirement.client.required` («Indica el cliente
representado.»), `CFR02` → 400 `…client.inactive`; the status `PATCH` that publishes or resumes answers 409 with
`reason` `CLIENT_REQUIRED` / `CLIENT_NOT_ACTIVE` (`RECRUITER_CONFLICTS`, SQLSTATE `CFR01…`). Requirement rows embed
`represented_clients ( id, name, status )` (agency members under RLS) as `client`. `opportunities` (both views) maps
`list_opportunities.client_name` to `clientName`; `applications` answers 409 `CLIENT_NOT_ACTIVE` for an application or
a forward step on a revoked representation.

### No service role for account deletion or invitation e-mail (PKG account, decided 2026-10-23)

- **Account closure** deletes the Auth user from SQL: `close_my_account()` is SECURITY DEFINER, its owner may delete
  from `auth.users` (the Auth tables' own foreign keys cascade sessions, identities and tokens), and the body only
  ever deletes `auth.uid()`. One transaction with the closure rules (migration `20261023400100`), so no half-closed
  account if a rule refuses. The Admin API (`auth.admin.deleteUser`) would have needed the service role for the same
  effect. Existing access tokens stay valid until they expire (≤ 1 h) but every refresh fails and no profile is left
  to read; the web app clears the device's cookies right away.
- **Invitation e-mail.** Supabase Auth only e-mails addresses that have an Auth user, and `inviteUserByEmail` (service
  role) would create the account at invitation time — the opposite of v1.8's «register with a code». The public
  `signInWithOtp` creates a throw-away delivery account instead; it gets no profile (sign-up trigger), is deleted by a
  platform-admin RPC right after Auth sent the message, and its own link is useless (PKCE verifier discarded). The
  invitation code is the credential; the e-mail only carries it. Local template:
  `supabase/templates/confirmation.html`; production template and redirect URL are owner settings (with
  confirmation off Auth uses the magic-link template; the first `ALLOWED_ORIGINS` entry must be the app's origin).

### Service role — `documents-maintenance` (the only exception, LOCAL ONLY)

**Why.** Purging a deleted document's bytes means removing a Storage object, which is possible only through the
Storage API, and those objects belong to other users or to deleted accounts. The owner-only Storage policies
deliberately give a platform admin's JWT no access to them, and there is no SQL path that deletes Storage
objects safely. **Authorization.** The function answers 404 unless `DOCUMENTS_MAINTENANCE_ENABLED=true`, then
requires a JWT whose user the database reports as platform admin (`is_platform_admin()`), and every RPC
re-checks that in its body. **Exception (N-19, LOCAL `20261024200000`):** the env flag guards the service-role
Storage delete, not the RPCs; `document_maintenance_batch(true, …)` called by a platform admin straight through
PostgREST also expires the trash — it deletes only archived documents past `archive_retention`, re-checked on the
locked row, each audited `document.trash_expired`. Accepted on purpose (security review LOW-1): a second owner flag
would leave the documented retention silently inert, and the deletion is bounded by that retention and audited. **Scope.** The service-role client is created only in the apply path, after that
check, and is used for exactly one call: `storage.from('professional-documents').remove([path])`, one path at
a time, only after `document_purge_recheck` (row lock; no row references the path, no legal hold, due, not
purged) allowed exactly that path — a pure planner (`documents-maintenance/plan.ts`) refuses any mismatch or
malformed path. It never queries tables. **Audit.** Each purge writes `document.purged` through the caller's
JWT (actor = the platform admin; ids and reason only). `tests/security/repo-hygiene.test.ts` fails if any other
function file mentions the service role. Alternative considered: a local operator script holding the key
instead of a deployable endpoint — smaller exposure, but no platform-admin check; left to the owner.
