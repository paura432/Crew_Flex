# Security & Privacy

> **Local vs production (2026-10-15).** Production has only migrations `20261009120000` and `20261009120100`.
> Every object, rule enforcement or control below that cites a migration dated `20261011…` or `20261015…`
> exists **only in the local database** until the authorized rollout (`docs/audit/CREWFLEX_DIFF_CURRENT.md` §5;
> state in `memory-bank/01-current-state.md`).

Priority order: **security > domain correctness > data integrity > product clarity >
maintainability > UI polish > feature count.**

## Structural rules

1. `SECRET ≠ PUBLIC ENV`. Only `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`
   exist in the frontend. Backend secrets live in **Supabase Edge Function Secrets**
   (`supabase secrets set NAME=value`) and are read at runtime with `Deno.env.get`.
2. `NEXT_PUBLIC_SUPABASE_SERVICE_ROLE_KEY` must never exist. A repo test fails if `service_role`,
   `SERVICE_ROLE` or `sb_secret_` appear under `src/`.
3. Default execution context is **user JWT + RLS**. Service role is not used anywhere in V0.
4. Identity comes from the verified JWT (`auth.getClaims`). Payload schemas are `.strict()`, so a
   body `userId` / `role` is rejected, never trusted.
5. Errors returned to clients are normalized (`code` + safe message + `requestId`). No stack
   traces, SQL, Supabase internals, tokens.
6. Logs: function, requestId, actorId, duration, result. Never Authorization headers, passwords,
   tokens, documents, secrets or full payloads.

## Matchable vs shareable data

`get_requirement_candidate_pool()` returns, for external candidates, only: a per-requirement
pseudonymous reference, base location, years of experience, the qualifications **relevant to the
requirement** (type, status, verification, expiry) and availability windows **overlapping the
requirement**. Display name only if visibility = `open`. No email, phone, documents, employer, rates.
Its companion `get_requirement_candidate_passports()` (LOCAL, package passport) adds, for the same rows and
references, the declared main category, categories, aircraft, English, work permits and a `has_restrictions`
flag — still no contact, employer, rate, blocks or restriction text.

## Privacy by design

- Default visibility `private`. The profile never becomes a public directory automatically.
- Applying is the professional's own act of disclosure (D-06/D-12, LOCAL `20261022130300`): the applicant becomes
  visible to **that** organization for **that** requirement only, under the candidate-pool rules (per-requirement
  pseudonym unless internal, name only for internal or `open`, relevant qualifications and overlapping windows; no
  contact data, no documents — D-07 not activated). `private` professionals are still never in the external pool.
- Professionals read published requirements only through a fixed projection (`list_opportunities`: organization
  name, no ids of people or organizations, no counts of other applicants).
- Application audit rows whose actor is the technician carry no organization id, and covered ↔ open status
  changes made by an application carry no actor, so an organization's audit trail never holds an applicant's
  profile id (T-04).
- In-app notices (v2-18, LOCAL `20261023800000`, T-70…T-73) reveal **nothing the reader could not already see**: the
  row stores ids and enums only (recipient, kind, application, status reached) — no free text, no reason, no other
  person's id. The text is rendered when read: a technician sees the requirement title, its organization's name and
  the new status (what «Mis candidaturas» shows); an organization admin/manager sees the requirement title, the status
  and the applicant under the candidate-pool rules of **today** (`CF-…` pseudonym unless internal; name only for
  internal or `open`), and only while they still hold that role. Plain members never receive them; nobody reads
  another person's notices (no platform-admin path either). In-app only: no e-mail, SMS, push or WhatsApp (OUT).
  No API role can read or write the table: only the two read RPCs and `mark_notifications_read` (own rows).
  **Retention and volume (T-71, T-73):** 180 days and the newest 200 per recipient, never listed beyond that and
  pruned when the recipient gets a notice or marks one read (no scheduler: an older row of an inactive recipient
  stays stored, unreadable, until then); while unread, a notice takes the next event about the same technician and
  requirement (pause/resume toggles and apply/withdraw loops update one row), so a loop by the other party cannot
  push a recipient's other notices out; only many distinct events (other applicants or requirements) reach the cap,
  which then drops the oldest. Deleted with the application, the requirement or the
  account; an organization recipient's notices are deleted when they lose admin/manager (the event trigger locks
  the memberships, so a concurrent demotion cannot leave one behind). Marking read is the only write a user makes.
- Internal workforce data visible to own organization admins/managers only (OD-4).
- Contact and economic data of the passport (LOCAL, package passport `20261023100100`): phone, current employer,
  minimum rate and blocked organizations live in owner-only tables (`technician_private_details`,
  `technician_organization_blocks`): not readable by the own organization or platform admins, written only by the
  DEFINER passport save, and returned by no function to anyone else (D-07 P1: contact is shared only with its
  consent, and that sharing path does not exist yet). A blocked organization is not told; it simply no longer
  finds the professional in its external pool (T-35). **Residual risk (T9, security review LOW-1):** it can still
  infer a block — the external pool summary drops by one when the block is saved, and a second organization
  account posting the same need would see an `open` (or recognisable: base, years, expiry dates, declarations)
  professional that the first no longer sees. The declarations also add quasi-identifiers to pseudonymous rows,
  although base, years and exact expiry dates already make them linkable (T-04).
- To block, professionals see only organizations that have published at least once, their memberships and their
  own choices (`list_blockable_organizations`), never the whole organization directory (review MEDIUM-1).
- Audit metadata contains ids and counts, not personal data.

## Account closure — what is deleted and what stays (T-42, LOCAL `20261023400100`)

**Deleted at once**, whatever deletes the account (the «Cerrar cuenta» button, the Auth Admin API, the dashboard):
credentials (Auth user, sessions, identities, one-time tokens), the profile, the technician profile with its
qualifications (and the reviewer's note on them), passport declarations, type ratings, owner-only details
and organization blocks, the logbook, availability windows and saved rotation, notices addressed to them, memberships,
idempotency keys, every invitation of the address (they hold it) and the document rows. The documents' bytes:
removed right after the closure with the person's own token; anything Storage leaves is a due `owner_delete`
tombstone purged by `documents-maintenance` (`DOCUMENT_WALLET.md` §6). An operator deletion without the button
keeps the wallet's `account_deleted` grace (30 days, owner proposal).

**Kept, without the profile** (to settle the operational history, v1.8): applications (status, proposal versions,
timeline; `technician_profile_id` NULL — nobody can link them to a person any more except through the ids below),
requirements the person created (`created_by` NULL), the organization and its other members, and **audit rows**:
their actor becomes NULL; ids already in metadata (application, requirement, the closed profile's own id in
`account.closed`, `technician_profile_id` in `qualification.*` and `document.*` rows) stay. Audit rows hold ids and
flags only (S-9), never names, e-mail addresses, codes or free text. No retention period is set for them (as for the
rest of the audit trail; D-07 P3 stays open).

**Refused** while the person has an `accepted` or `confirmed` application, or is the last admin of an organization
with one: «Resuelve primero los compromisos aceptados o confirmados.» Nothing changes until it is resolved.

## Sessions and e-mail confirmation (local Auth; production Auth is the owner's)

- Session timebox **12 h** from sign-in (`[auth.sessions] timebox`, v1.8 `Max-Age=43200`, T-44): after it the refresh
  fails and the proxy sends `/app/**` back to `/login?next=…`. Not verified end to end (it needs a 12-hour run).
- E-mail confirmation **on** (T-41): sign-up links (1 h, `otp_expiry` shared with recovery) land on the login; the
  local template `supabase/templates/confirmation.html` also carries the invitation e-mail (T-40). Production needs
  the owner to enable confirmation, add `…/auth/confirm` and `…/register` to the redirect allow-list and apply
  the template (with confirmation off Auth sends the **magic link** template for the invitation instead), and the
  `invitations` function's first `ALLOWED_ORIGINS` entry must be the production origin.
- Unused invitations (revoked or expired) keep an address of someone who never signed up for 30 more days; they
  are deleted by the next invitation (T-40). Audit rows of invitations carry no address.

## T22 · Password change — provider evidence (2026-10-20, local GoTrue v2.197.0)

`scripts/local/t22-auth-matrix.mjs` (throw-away local clones, one flag each; synthetic users deleted):

| Case                                                             | Default (today) | `require_current_password`              | `secure_password_change`         |
| ---------------------------------------------------------------- | --------------- | --------------------------------------- | -------------------------------- |
| Ordinary session < 24 h, new password only (`PUT /auth/v1/user`) | **200 (gap)**   | 400 `current_password_required`         | **200** (recent sessions exempt) |
| Wrong / correct `current_password`                               | —               | 400 `current_password_invalid` / 200    | —                                |
| Session > 24 h                                                   | **200**         | 400                                     | 400 `reauthentication_needed`    |
| Legitimate recovery link, no current password                    | 200             | **200** (`session.IsRecovery()` exempt) | 200                              |
| Other sessions after a change                                    | revoked         | revoked                                 | revoked                          |

Source check (supabase/auth `internal/api/user.go`): the current-password check is skipped only for
`session.IsRecovery()`; reauthentication applies only when the session is older than 24 h. A recovery link
verified with `token_hash` carries `amr` `otp`, a PKCE `code` link carries `recovery` — the app gate accepts both.

**Limits (review of `5d22175`):** GoTrue's `IsRecovery()` also covers sessions opened by magic link or e-mail
OTP and has **no time limit** (the AMR survives refresh). Mitigation in the app: after a reset every session
ends, the recovery one included (`signOut({ scope: "global" })`, V1.8 A:165), so no long-lived recovery session
remains. Residual: a session opened by magic link / e-mail OTP keeps the exemption — the app never offers those
sign-ins, but GoTrue's `/otp` is reachable while the e-mail provider is on. Users without a password and MFA
(AAL2) rules are out of this matrix. **Also an owner check:** production must keep secure e-mail change
(`double_confirm_changes`) on, otherwise a stolen session takes the account through an e-mail change.

**Recommendation:** enable **require current password** (Management API `security_update_password_require_current_password`,
dashboard Auth → Providers → Email) in production. `secure_password_change` adds nothing for sessions < 24 h
and would force a nonce e-mail on old sessions; optional. Recovery keeps working (exempt). The app has no
«change password» screen outside recovery, so no UI change is needed. Local CLI 2.120 cannot set the flag in
`config.toml` (only `secure_password_change`): local parity is the clone test above. **Production Auth is
not modified without owner authorization.**

**Redirect allowlist (S-4):** `scripts/local/redirect-allowlist-check.mjs` 6/6 — external, `null`,
look-alike (`localhost:3001.evil…`, `localhost:3001@evil…`) targets fall back to `site_url`; `next=//…` is
neutralised by `safeConfirmNext`. Production must list only `https://crew-flex.vercel.app/**` (owner check).
