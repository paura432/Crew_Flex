**Package passport (LOCAL `20261023100*`), extends S-5/S-7/S-10:** the v1.8 passport columns and tables have no
write grant — `save_professional_passport` (DEFINER, `auth.uid()` rows only) is their only writer; phone,
employer, rate and blocks are owner-only; a professional who blocked an organization is not in its external pool
(`ranked_external_pool`); organizations read candidates' declarations only through
`get_requirement_candidate_passports`, which calls the pool function (same rows, pseudonyms, cap and role check).
Proof: `tests/db/passport.test.ts`.

**Package professional-block (LOCAL `20261024800000`, v2-16, T-160), extends S-7/S-10:** the passport's blocks also
bind the professional's own side — `list_opportunities` (and so the detail by id and a member's network view) and
`get_requirement_profile_rules` never return a blocked organization's requirement, `apply_to_requirement` refuses it
(`CFA16` after the state, before the history and eligibility) — through one private predicate
`app_private.technician_blocks_organization(profile, organization)` (INVOKER, `search_path = ''`, no execute for
`public`/`anon`/`authenticated`), always evaluated for `auth.uid()` only. Existing applications, pools, counts,
directory and outreach are unchanged; the pool bodies (`ranked_external_pool`, `count_viable_candidates`,
`count_visible_network`) keep their inline copy, each pinned by its own test (the directory package re-creates
`count_visible_network` and adds a copy in `directory_visible`; the helper's profile parameter is for them — a public
function passes the caller only). Proof: `tests/db/professional-block.test.ts`.

**Package wallet-extras (LOCAL `20261024200000`), S-10 and the maintenance gate:** `document_maintenance_batch`
checks `auth.uid()` and the platform role in its body (S-10 holds), but since N-19 its apply mode also **deletes
document rows** of any owner — only archived ones past `archive_retention`, each audited `document.trash_expired` —
and that deletion does **not** depend on `DOCUMENTS_MAINTENANCE_ENABLED` (a function env that guards only the
service-role Storage delete): a platform admin calling the RPC through PostgREST expires the trash. Explicit,
documented exception (EDGE_FUNCTIONS.md); the expiry re-checks its condition on the locked row, so a document
restored meanwhile is kept (`scripts/local/db-race-check.sh wallet-trash`). `document_trash_retention_days()` answers
null without a JWT subject. Proof: `tests/db/wallet-extras.test.ts`.

**Package recruiter (LOCAL `20261024500000/500100`, BR-27), extends S-3/S-7/S-9/S-10/S-16:** a represented client is
read only by the members of its agency and platform admins; nobody writes `represented_clients` or
`work_requirements.on_behalf_of_client_id` directly — the DEFINER RPCs check role and organization type in the body
(missing = not allowed, 42501), activation is a platform admin's act with evidence apart, never for an agency they
belong(ed) to or acted for. BEFORE triggers bind every path: only an active representation of the requirement's own
organization, an agency never publishes or resumes without one (CFR01/CFR02), the client changes only on a draft,
no application (CFA01 to the applicant) or forward step (CFR02) while not active, a stranger gets 42501 before any of
it (no oracle), and the organization type cannot flip around the rules (BR-27.7). The contact e-mail has no column
grant (admins/managers and platform admins through `list_represented_clients`). Professionals and other organizations
get the client's name only (via `list_opportunities`), never its e-mail or id. Proof: `tests/db/recruiter.test.ts`,
`db-race-check.sh recruiter`.

**Package outreach (LOCAL `20261024400000`…`400200`), extends S-7/S-9/S-10:** «Distribuir aviso Urgente / AOG» is
one DEFINER function (`requirement_outreach`): admin/manager from the database (checked before the row lock), the
audience read inside it (external pool rules: never `private`, never a member, never a blocker), and the organization
learns **only the count** — no recipient in the answer, in `outreach_distributions` or in the audit metadata, and no
number below 5 eligible professionals (T-128; residual SECURITY_PRIVACY T43); notice preferences are owner-only. Proof: `tests/db/outreach.test.ts`, `db-race-check.sh outreach` (two clicks, one run).

S-7 also binds the applicant label of organization-side notices (`get_my_notifications`, LOCAL `20261023800000`):
the same pool rules as `get_requirement_applications`, applied at read time (`tests/db/notices.test.ts`).

**Package pack-view (LOCAL `20261024300000`), extends S-7/S-10:** applying also freezes a Candidate Pack copy
(`application_packs`, no API grant) readable only by the applicant and the requirement organization's admins/managers
at reading time, through `get_application_pack` (anyone else: `P0002` like a random id); its fixed columns never carry
name, contact, employer, blocks or documents; it is wider than the S-7 card (every active qualification, the
restriction texts, the minimum rate and the selected logbook entries — the owner's previewed act, T-111/T-112);
withdrawal, rejection, cancellation and account closure delete it; only the applicant's own insert writes one.
Residuals (free text, cross-requirement linkability): `SECURITY_PRIVACY.md`. Proof: `tests/db/pack-view.test.ts`.

**RLS does not protect a SECURITY DEFINER function.** Inside one, the function body is the only
authorization. Review every DEFINER for S-10 and test the "other organization" and "other user" cases.

## Roles (summary — matrix in AUTHORIZATION.md)

`profiles.account_type` routes the UI and grants **nothing**. Permissions come from
`technician_profiles` ownership, `organization_members.role` (`member` < `manager` < `admin`) and
`profiles.platform_role` (`platform_admin`). Plain `member`s do not see colleagues' technician data.

## Multi-tenancy

Every org-scoped policy goes through `is_org_member` / `has_org_role`. A user acts for one organization
in the UI (`requireOrganizationContext` picks the highest role); the database does not assume that.
Cross-org access returns 404 in the UI (evidence `docs/audit/evidence/remediation-2026-10-15/local-09-cross-org-404.jpg`).

## Agent prohibitions

- No `NEXT_PUBLIC_*SERVICE*`, no service role, no `sb_secret_` anywhere in the repo.
- No disabling/weakening RLS, no broad `grant … to authenticated` to make a test pass.
- No `supabase db push`, `db reset --linked`, `functions deploy`, `secrets set`, Auth setting change or
  any remote write without the owner's explicit authorization **for that action**.
- No editing an applied migration; add a new one.
- No real personal data in seed, fixtures, tests, docs, logs or the memory bank.
- No printing `.env*` contents; check targets with `grep` on the URL only.

## Regression scenarios to re-run after security-relevant changes

User B edits user A's passport/qualification/window → 403/404 · member of org X reads org Y's requirement
→ 404 · plain `member` runs matching → 403 · professional sets `verification_status` → rejected ·
organization reads `review_note` → permission denied · platform admin reviews own qualification → 403 ·
review with stale version → 409 · `private` professional appears in external pool → never · same
`Idempotency-Key` with another payload → 409 · direct PostgREST delete of last hard qualification → rejected at commit · organization reads `applications` directly → 0 rows · technician shortlists own application → 403 · another organization transitions an application → same 404 as a random id · confirm the last seat twice → one wins (`db-race-check.sh applications`) · edit a requirement that received an application → 409 `HAS_APPLICATIONS` · close with an accepted/confirmed application → 409 `ACTIVE_COMMITMENTS` · a stranger inserts a qualification on a published requirement → 42501 whatever its applications or closure (no oracle) · another user (other organization, plain member, platform admin) reads or marks someone's notice → 0 rows · a demoted or removed manager keeps no notice of that organization (`tests/db/notices.test.ts`) · another organization, a plain member, another technician or a platform admin reads an application's Candidate Pack copy → `P0002` like a random id; the copy does not change after the passport or logbook does; withdrawal, rejection, cancellation or account closure deletes it; a row written by anyone but the applicant gets none (`tests/db/pack-view.test.ts`) · requirement builder (LOCAL `20261023600000/600100`): an admin/manager updates `conditions`/`shifts`/`archived_at` through PostgREST → 42501 (RPC only) · un-archiving, even as owner → 55000 · a member, another organization or a professional asks the live count (`count_viable_candidates`) or archives → 42501 · the count never includes `private` professionals · recruiter (LOCAL `20261024500000/500100`): another agency, a plain member or a professional adds/revokes a client → 42501; a platform admin activates a client of an agency they belong(ed) to → 42501; an agency publishes without a client → CFR01; a pending/revoked client on publish, resume, apply or confirm → CFR02; the client changes after an application → CFA12 · v1.8 profile requirements (LOCAL `20261023900*`): an admin/manager writes a rule column through PostgREST → 42501 · an organization or anon reads `get_requirement_profile_rules` → 42501, a professional gets only published/current or applied-to requirements · a candidate row never carries restriction text, and only the asked engines/capabilities/ratings · applying or confirming against a failed rule → CFA14, confirming with declared general restrictions → CFA15.
