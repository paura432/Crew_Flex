**Package passport (LOCAL `20261023100*`), extends S-5/S-7/S-10:** the v1.8 passport columns and tables have no
write grant — `save_professional_passport` (DEFINER, `auth.uid()` rows only) is their only writer; phone,
employer, rate and blocks are owner-only; a professional who blocked an organization is not in its external pool
(`ranked_external_pool`); organizations read candidates' declarations only through
`get_requirement_candidate_passports`, which calls the pool function (same rows, pseudonyms, cap and role check).
Proof: `tests/db/passport.test.ts`.

S-7 also binds the applicant label of organization-side notices (`get_my_notifications`, LOCAL `20261023800000`):
the same pool rules as `get_requirement_applications`, applied at read time (`tests/db/notices.test.ts`).

**RLS does not protect a SECURITY DEFINER function.** Inside one, the function body is the only
authorization. Review every DEFINER for S-10 and test the "other organization" and "other user" cases.

## Roles (summary — matrix in AUTHORIZATION.md)

`profiles.account_type` routes the UI and grants **nothing**. Permissions come from
`technician_profiles` ownership, `organization_members.role` (`member` < `manager` < `admin`) and
`profiles.platform_role` (`platform_admin`). Plain `member`s do not see colleagues' technician data.

## Multi-tenancy

Every org-scoped policy goes through `is_org_member` / `has_org_role`. A user acts for one organization
in the UI (`requireOrganizationContext` picks the highest role); the database does not assume that.
Cross-org access returns 404 in the UI (evidence `docs/audit/evidence/remediation-2026-10-15/local-09-cross-org-404.jpg`).

## Agent prohibitions

- No `NEXT_PUBLIC_*SERVICE*`, no service role, no `sb_secret_` anywhere in the repo.
- No disabling/weakening RLS, no broad `grant … to authenticated` to make a test pass.
- No `supabase db push`, `db reset --linked`, `functions deploy`, `secrets set`, Auth setting change or
  any remote write without the owner's explicit authorization **for that action**.
- No editing an applied migration; add a new one.
- No real personal data in seed, fixtures, tests, docs, logs or the memory bank.
- No printing `.env*` contents; check targets with `grep` on the URL only.

## Regression scenarios to re-run after security-relevant changes

User B edits user A's passport/qualification/window → 403/404 · member of org X reads org Y's requirement
→ 404 · plain `member` runs matching → 403 · professional sets `verification_status` → rejected ·
organization reads `review_note` → permission denied · platform admin reviews own qualification → 403 ·
review with stale version → 409 · `private` professional appears in external pool → never · same
`Idempotency-Key` with another payload → 409 · direct PostgREST delete of last hard qualification → rejected at commit · organization reads `applications` directly → 0 rows · technician shortlists own application → 403 · another organization transitions an application → same 404 as a random id · confirm the last seat twice → one wins (`db-race-check.sh applications`) · edit a requirement that received an application → 409 `HAS_APPLICATIONS` · close with an accepted/confirmed application → 409 `ACTIVE_COMMITMENTS` · a stranger inserts a qualification on a published requirement → 42501 whatever its applications or closure (no oracle) · another user (other organization, plain member, platform admin) reads or marks someone's notice → 0 rows · a demoted or removed manager keeps no notice of that organization (`tests/db/notices.test.ts`) · requirement builder (LOCAL `20261023600000/600100`): an admin/manager updates `conditions`/`shifts`/`archived_at` through PostgREST → 42501 (RPC only) · un-archiving, even as owner → 55000 · a member, another organization or a professional asks the live count (`count_viable_candidates`) or archives → 42501 · the count never includes `private` professionals.
All automated in `tests/db/rls.test.ts`, `tests/db/requirement-builder.test.ts`, `tests/e2e/*` and `scripts/local/db-race-check.sh`.
